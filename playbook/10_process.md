# 10 進め方：フェーズ、チーム、レビュー、ゲート

## 1. 全体の流れ

```
ブリーフ確認 → 素材分析 → ┬ 内容計画（構成・原稿・図解・正確さ）┬→ 絵コンテ承認【ゲート1】
                          └ 編集計画（曲・カット割り・動き・音）┘
 → デザイン（色・文字・部品・焼き込みの処理）【ゲート2】
 → アニマティック v4.1 → 書き出し＋自動QC＋独立レビュー → 直す → v4.2 → …【ゲート3：試写1】
 → （対抗案 B を作って並べる → 選ばれた案を磨く：チームレビュー → 監督の統合）
 → 本制作【ゲート4：試写2＝技術監修、試写3＝対象者テスト】 → 本ナレ差し替え・最終ミックス【ゲート5】
```

フェーズの表とゲートで出すものは AGENTS.md にある。ここでは、今回それぞれの段階で**何が効いたか**を書く。

## 2. 段階ごとのやり方

### 2.1 ブリーフ確認（docs/01）
- 「このパートが運ぶもの」を一文で決める。今回は依頼者の指摘（「測量部門は複数の作業の紹介があり、その中の1作業でしかないのに、基準点だけで満たそうとしすぎ」）で、**「ほかの測量が使う“位置の目印”をつくる作業」**に絞り直した。会社全体の社会的意味は、このパートでは背負わない。
- 家族が持ち帰る言葉を3つ決め、試写3で本当に言えるかを確かめる（docs/07 §4）。

### 2.2 素材分析（docs/02、analysis/shot_log.md）
- カットごとに IN/OUT、焼き込みテロップの位置（ピクセル）、カメラの動き、使える静止フレーム、写っている物（人・道具・地面）を表にする。
- **足りない画**をはっきり書く（今回：基準点の標識そのもの、完成した道路や地図）。足りない画は図解で補うか、人に撮影を頼む。AI の生成画像で現場や人を作らない。
- 焼き込みテロップは「切り出す」「覆う」をカットごとに並べて比べ、選んでもらう（今回は切り出し：S01・S02 は1.41倍、S03 以降は1.2倍）。

### 2.3 内容計画と編集計画を分ける（今回いちばん効いたこと）
依頼者の言葉：「作り始める前にどれだけしっかり考えて作るかが大事」「内容だけじゃなくて、編集面も大事」。
- **内容計画**（templates/content_plan.md、実例 reference/plans/content.md）：このパートの役目、前の案の弱点の表、案の比較（推奨・不採用とその理由）、拍の表（拍・小節・時間・画・ナレ・文字・**目的**）、原稿、図解の仕様、決めてほしいこと、【要監修】。
- **編集計画**（templates/editing_plan.md、実例 reference/plans/editing.md）：曲の地図（小節ごとの強さ・楽器）と編集点、24小節のカット割り、リズムの決まり、カメラの動きを使う所（3か所だけ）、つなぎ（ディゾルブは1か所だけ）、文字、図解の動き、色、ミックス、シリーズ共通の型、残るリスク。
- 2つの計画は別の担当（別セッション）が書き、最後に突き合わせる。内容担当は「何を言うか」、編集担当は「いつ・どの音の上で見せるか」に責任を持つ。

### 2.4 絵コンテ（ゲート1）
- 拍ごとに：時間、画のサムネイル、ナレ、文字、図解のラフ、音、**目的**。目的を言えない要素は入れない。
- 今回は計画書のカット割りを、元素材のサムネイル入りの縦長シート（plan/editing_storyboard.png、scripts/43_edit_storyboard.py）にした。QC はこのシートと書き出しを並べた比較（qc/<版>/storyboard_compare.jpg）を毎回つくる。

### 2.5 アニマティック → 本制作
- まず全編を粗く通す（仮ナレ・仮の曲・粗い図解）。部分を磨き込む前に、構成とリズムを見てもらう。
- 依頼者は「実際に動くものを見て判断できるほうが早い」と考える人だった。ゲート1の資料と同時にアニマティックまで作って出し、好みが分かれる判断は暫定値で進めてゲートでまとめて聞いた（docs/decisions.md）。

### 2.6 書き出すたびのループ（毎版）
1. `bash scripts/60_render.sh v4.x`（timeline → ミックス → index → lint → 書き出し → 自動QC）
2. qc/v4.x/report.md の FAIL と WARN を読む。0件の検査は FAIL 扱い。
3. 目視用シートを自分で見る：contact_0p5s（0.5秒ごと）、text_strips（画面の文字ごとに出た直後・中間・消える直前＋等倍の小窓）、storyboard_compare、hf_review、levels.png。
4. **独立レビュー**（§4）。
5. 指摘ごとに「対応／据え置き（理由）／依頼者に聞く」を docs/decisions.md に書く。
6. 直して次の版。レビューが「試写に出してよい」と言い、重要な指摘が残っていなければ人に出す。

今回の独立レビューの指摘の推移：v4.7 は重要4件 → v4.8 は重要2・軽微2 → v4.9 は軽微3 → v4.10 は軽微2（試写に出してよい）。

## 3. チームで見る（磨き込み）

依頼者の言葉：「様々な視点からチームとして取り組んで」「監督として、各担当スレッドの改善案をまとめるだけでは監督の意味がない」。

### 3.1 視点（今回の9つ）
| 担当 | 見るもの | 返すもの |
|---|---|---|
| 構成・技術監修役 | 伝わる順番、事実の正しさ、用語 | 壊してはいけないもの3つ、改善案の表、【要監修】 |
| 編集 | カットの位置、拍、つなぎ、静止、寄り | 同上＋拍と秒の具体値 |
| デザイン（モーショングラフィックス） | 文字、図解、色、動きの規則（docs/04） | 同上 |
| ナレーション演出 | 原稿、読み、間、アクセント、声の高さ | 原稿の全文案＋文ごとの読み方 |
| 音響 | ナレと曲の差、効果音の聞こえ、余韻 | 数値の測定＋試聴用の mp3 |
| 内容（別担当） | 構成の弱点、原稿の別案 | 原稿 v3.2 案、試写3で確かめること |
| 編集（別担当） | 語ごとのナレと画のタイミング（実測） | タイミング表 |
| 正確さ監修 | 用語、比喩、図解の幾何 | 監修意見、測量士への質問（選択式） |
| 音（別担当） | ミックスの作り直し案 | 試聴用の音（T0〜T4）と鍵の数値 |

- 全員に同じブリーフ（prompts/20_role_reviews.md、実例 reference/plans/brushup/director_team/00_BRIEF.md）を渡す。見るファイル、守る制約、返す形（壊してはいけないもの3つ以内、改善案の表：ID・優先度 A/B/C・時刻・問題・具体的な直し方（数値・文言・秒）・理由、対抗案から取り入れられるもの）をそろえる。
- 担当は作業ファイルを自分のフォルダにだけ書く。本体（リポジトリ）は読むだけ。

### 3.2 監督の統合（prompts/30_director_synthesis.md）
- 案を数で取り込まない。原則（00_summary.md の5つ）で**採用・見送り・依頼者に選んでもらう**に分け、見送りにも理由を書く。
- 監督は自分でも推論して案を足す。担当の案どうしがぶつかる所（例：効果音を目立たせたい音響 vs 言葉を聞かせたいナレ演出）は、原則の順で決める。
- 出すもの：監督メモ（採用した改善の表：場所・変えたこと・ねらい・出典ID／見送った案と理由／依頼者に選んでほしいこと：選択肢と監督のおすすめ／既知の問題と測量士に聞くこと）。

## 4. 独立レビュー（prompts/40_independent_review.md）

- **作り手と別のセッション**で、コードやスクリプトを見せずに行う。渡すのは：ブリーフ（docs/01）、規定（docs/04 §8 など）、原稿、qc/<版>/report.md と目視用シート。`bash scripts/45_review_pack.sh v4.x` が qc/v4.x/review_pack/ にまとめる。
- 返す形：表（タイムコード｜重さ（重大／重要／軽微）｜問題｜根拠（どの画像・どの数値）｜直し方）と、最後に「試写に出してよいか：はい／いいえ（理由）」。結果は qc/v4.x/review.md。
- 指摘への対応は作り手が決め、decisions.md に書く。据え置く指摘は理由を書く（例：0.07秒の間隔の不足は「多くの人には気づかれない」ので試写1で確認）。

## 5. ゲートで依頼者に見せる

- 依頼者はスマホで見る。**メッセージは短く**、見るものは添付（mp4、シート画像、ドキュメント）。
- 出すもの：(1) 見るファイルと見方、(2) 決めてほしいこと（5問以内、選択肢つき、おすすめ1つ）、(3) 既知の問題。
- 好みの判断は**比べられる形**で出す：声の案 A〜F を1本のファイルに並べる、曲の候補3つ、色補正3案を1枚に、などの比較用ファイルを作る。
- 依頼者の決定は decisions.md の「決めた人」に依頼者と書く。

## 6. 対抗案（prompts/50_rival_version.md）

- 依頼者に「1案だけだと比較できない」と言われたら、**意図して違う**案を、同じ品質基準・同じ素材で、別のフォルダ（別ブランチ）に作る。違いを5つ先に決めて崩さない（今回の B案：入り方、画づくり、図解のしかた、語り、締め）。
- 比べた結果は、勝った案の磨き込みに使う（何が効いたかの言語化と、負けた案から取り入れるものの検討）。

## 7. 記録と版

- **docs/decisions.md**：日付｜フェーズ｜決めたこと｜理由｜決めた人。新しいセッションはここを最初に読む。
- **docs/credits_and_licenses.md**：素材を使う前に規約を読み、確認日とともに書く。
- 版の名前は `v<フェーズ>.<連番>`。renders/・qc/ のフォルダ名とコミットの題（「v4.10：…」）をそろえる。
- 見送った案・未決の選択も記録する。次の制作者が同じ議論を繰り返さないため。

## 8. Codex での回し方

Codex（CLI でもクラウドでも）では、Claude Code のスレッドやサブエージェントの代わりに「別のセッション（別のタスク）」を使う。

| 今回の形 | Codex での形 |
|---|---|
| 制作スレッド（監督） | メインのセッション。リポジトリの根の AGENTS.md に従う |
| 担当スレッド（内容・編集・正確さ・音） | 別のセッション／タスクに prompts/20_role_reviews.md の担当分を渡す。書き込みは reviews/<版>/<担当>.md だけ |
| 独立レビュー（サブエージェント） | `bash scripts/45_review_pack.sh v4.x` で作ったフォルダだけを開いた新しいセッション。そのフォルダの AGENTS.md がレビュアーの指示になる |
| 対抗チーム | 別ブランチ（例 `teamB/`）の別セッション |

- 同じセッションで自分の作品をレビューしても、独立レビューの代わりにはならない（作った理由を知っているので、見る目が甘くなる）。
- クラウド版で別タスクを並べられないときは、依頼者（人間）に「新しいタスクで qc/v4.x/review_pack を開いて、その AGENTS.md に従って」と頼む。
